Grounding Context

Codebase Context

Ovation is a white-label multi-tenant cricket stats platform: pnpm monorepo with a React 19 + Vite web app (artifacts/cricket-club, 58 pages), an Express 5 + Drizzle + Postgres API (artifacts/api-server, 48 route modules), an Expo mobile app, and an OpenAPI-first contract (lib/api-spec/openapi.yaml, 215 operations, generated hooks/Zod). Two data stores: the app Postgres DB (tenant-scoped curated content — the moat) and the read-only central PCA Postgres on Supabase (24 seasons, 27 clubs, 11,604 matches). Tenant context resolves per request through a single middleware chain; theming is runtime CSS-token injection from the tenant row.

The platform-admin console today can: authenticate platform admins, provision a tenant (resolve central club → upsert tenant row with a brand snapshot → mint the player_id_map crosswalk), list/detail tenants, patch plan/customDomain, and issue single-use admin password-reset links. It cannot delete tenants (no router.delete() exists; 30+ tenant-scoped tables have FKs with no cascades), cannot edit tenant branding (PATCH /platform/admin/tenants/:id touches only plan and custom domain, while provisioning hard-codes faviconUrl/secondaryColour/tertiaryColour to null), and cannot access a tenant's admin panel (the concierge workaround is issuing a reset link and waiting for a volunteer to redeem it). There is no audit table — reset-link issuance logs to stdout only. A fully-built self-serve branding editor (admin-branding.tsx: presigned uploads, client-side palette extraction, PATCH /tenant-brand) exists on the tenant side.

Institutional learning (central-read-player-identity-crosswalk.md): tenant deletion must sweep the crosswalk as the inverse of provisioning; crosswalk backfill must run idempotently through the shared minting helper; impersonation must be tenant-context substitution, not permission elevation, or central-read pages silently break; never write to the central DB.

External context: WorkOS impersonation (required reason, 60-minute auto-expiry, impersonator field driving a UI banner); Shopify's consent-gated "Allow assistance" pattern; impersonation audit events warrant the longest retention tier (~36 months); soft-delete plus a 30-day grace window is the dominant SaaS deprovision pattern; Brandfetch and Apify brand-extraction APIs (domain or Facebook page → logos + semantic colours); TeamLinkt sells a US$795 one-time "launch package" as a concierge onboarding upsell; AWS SaaS Lens treats tenant onboarding as an orchestrated pipeline with per-step state.

Ghost-session impersonation via tenant-context substitution

Description
A POST /platform/admin/tenants/:id/impersonate endpoint that requires a free-text reason and mints a short-lived ovation_ghost_session cookie carrying {platformAdminId, tenantId, reason, expiresAt}. The admin-auth middleware accepts it as a synthetic admin for that tenant only, and tenant context resolves to the target tenant through the existing resolution chain — so every central read filters by the right club and every crosswalk lookup resolves against the right tenant. Because platform and club sessions already live in different cookies, the ghost cookie coexists with the platform session: exiting is just clearing one cookie. Guardrails follow WorkOS: mandatory reason, 60-minute auto-expiry, a persistent "Ash is assisting — end session" banner in the tenant admin UI, and a durable audit row per mint/exit (see idea 7).
Basis
direct: the two session systems are already separate cookies (hhcc_session at lib/auth.ts:24, ovation_platform_session at lib/auth.ts:187 — verified); no impersonation endpoint exists; the current workaround is "issue reset link, wait for club admin to log in." external: WorkOS impersonation (reason + 60-min expiry + impersonator banner). The institutional crosswalk learning mandates substitution over elevation.
Rationale
This is the literal "access their admin panels" ask. Today every assist is synchronous with a volunteer's availability — you cannot fix a club's setup on a Tuesday night unless their secretary is at a laptop. Ghost sessions make assistance instant, credential-free, and time-boxed, and they route through the one seam (tenant-context resolution) that guarantees central-read pages keep working. It is also the substrate that lets the concierge reuse the club's own branding editor and future seeding wizards instead of duplicating those UIs in the platform console.
Downsides
It is a deliberate authz bypass in a system whose isolation tests currently guarantee cross-tenant rejection — the guardrail set (reason, expiry, banner, audit) needs explicit sign-off before any code. A counter-proposal exists (build scoped concierge endpoints instead and skip impersonation; see rejection D15) but under-delivers against the ad-hoc, long-tail nature of onboarding help. Ship only after (or with) idea 7's audit ledger.
2brandingConfidence 90%Complexity Medium

Concierge branding panel with one-input brand intake

Description
A branding section on the platform-admin tenant-detail page backed by a new PATCH /platform/admin/tenants/:id/brand endpoint that accepts the same UpdateTenantBrandBody shape as the self-serve editor, reusing the proven presigned-URL upload machinery. Layered on top: a one-input intake — paste the club's website or Facebook URL, and the tool fetches logo + colours (Brandfetch, with an Apify-style scrape fallback for Facebook-only clubs), runs the existing extractBrandPalette() logic server-side, previews the derived theme tokens in light and dark modes, and flags WCAG contrast failures before anything is saved. Concierge reviews a suggested brand card and clicks apply.
Basis
direct: PATCH /platform/admin/tenants/:id only updates plan/customDomain (verified at platform-admin.ts:220-260); provisioning writes faviconUrl: null, secondaryColour: null, tertiaryColour: null (provision.ts:126-131, verified); palette extraction already ships client-side (admin-branding.tsx:129-134, verified); seed-mandurah-tenant.ts hard-codes a KNOWN_LOGOS map as today's workaround. external: Brandfetch Brand API (domain → logos + semantic colour roles, free tier 100 req); Apify Fetch Branding for Facebook-only presences.
Rationale
This is the literal "upload their logos and set their club colours" ask, and it is mostly assembly: the schema, upload pipeline, and palette extraction all exist — the missing pieces are one endpoint, one UI panel, and the fetch assist. Every club provisioned today starts with two of three colours and the favicon literally null, and the only person who can fix it is a club admin who may not exist yet. Volunteer clubs rarely have a logo file at hand; "paste their Facebook URL, approve the card" is the shape of the actual concierge conversation.
Downsides
An external API dependency (build-vs-manual tradeoff worth a deliberate call — the free tier likely covers 27 pilot clubs, but scraping heuristics on Facebook pages are brittle). A counter-argument (rejection D11) says skip the platform panel entirely and set branding through the club's own editor via impersonation (idea 1) — one canonical editor, zero duplicated surface. The two compose: the endpoint is small enough to ship regardless, and the fetch assist is useful from either surface.
3tenant-deletionConfidence 85%Complexity Medium

Schema-derived deprovision engine with plan/apply

Description
A DELETE /platform/admin/tenants/:id capability built like terraform destroy: the sweep is derived at runtime by walking the Drizzle schema for every table carrying the shared tenantIdColumn(), ordered FK-safe. A plan mode returns exact per-table row counts ("this will remove 14 honour-board rows, 212 crosswalk rows, 3 admins…") before anything is touched; apply requires typing the tenant slug to confirm. A completeness test asserts the derived sweep covers every table in the _tenant.ts inventory, so adding a new tenant-scoped table can never silently orphan rows. Optionally, apply exports a signed JSON bundle of all rows to object storage before sweeping (undo artifact, data-portability deliverable, clone seed).
Basis
direct: no router.delete() exists in platform-admin.ts (verified); 30+ tenant-scoped tables have tenant_id FKs with no cascades (verified); the only deletion logic anywhere is a manual three-table sweep in test cleanup (platform-admin-tenants.test.ts:72-84, order admins → playerIdMap → tenants); _tenant.ts maintains the authoritative inventory + tenantIdColumn() helper (verified). The crosswalk learning requires deletion to sweep player_id_map as the inverse of provisioning.
Rationale
This is the literal "delete existing clubs" ask, and the derivation move is what makes it safe to own long-term: a hand-maintained delete list silently rots the first time a new tenant-scoped table ships, which the schema's own history shows happens regularly. Plan-mode dry runs give the concierge confidence before an irreversible act — the immediate use case (test tenants like test-coastal, mis-provisioned clubs) is exactly the "provision the wrong club and retry" loop the pilot phase generates.
Downsides
FK-safe ordering across 30+ tables needs care (or per-table onDelete policy decisions instead); Postgres sequence behaviour means a re-provisioned club may get different per-tenant player ints, so hard delete + re-provision is not identity-stable (the export bundle and idea 6's archive state both mitigate). Should be gated behind the lifecycle state machine (idea 6) so "delete" in the UI is usually a state transition, not a sweep.

Provision-as-pitch: pre-provision all 27 PCA clubs as draft tenants

Description
Run the idempotent provisioner across every club in central.clubs: 27 dormant tenants, each with slug, crosswalk, central-read stats, a generated monogram crest where no logo exists, and a staged brand kit — all in a draft status, unrouted and invisible. The concierge motion then inverts: instead of "sign up, then we build your site," the pitch is a reveal link to the club's already-live full-history site, and onboarding collapses to claim → consent → flip to live → hand over an admin reset link.
Basis
direct: provisioning is a three-step idempotent upsert (verified: provision.ts onConflictDoUpdate at line 142; the club_claimed check at lines ~106-115 is the only blocker, and draft-status pre-provisioning sidesteps it by being the claim). external: TeamLinkt sells a US$795 one-time launch package for exactly this white-glove setup; Ovation's central DB makes the same launch artifact nearly free to produce.
Rationale
The single idea that changes what Phase 1 is: not "onboard 2–3 friendly clubs" but "un-hide 2–3 of 27 finished sites." Marginal onboarding cost drops to near zero, the concierge function shifts from data-entry to sales, and a zero-web-presence club sees a century of its own stats before spending a minute. Every other survivor compounds it: brand intake furnishes the drafts, the lifecycle machine gates the reveal, premiers seeding fills the honour board, the health checks certify each draft.
Downsides
Requires the lifecycle status column first (idea 6) and a rework of the club_claimed invariant. Data-governance caution: pilot scorecard data is scraped, and CLAUDE.md's hard constraint ("do not commercialise on scraped data; pilot/non-commercial framing") means 27 pre-built sites must stay private reveal links, not public marketing, until licensing is resolved. Biggest build in the set; a 2-3 club dry run of the same machinery de-risks it.

Honour-board seeding from central.premiers with provenance flags

Description
A concierge seeding wizard that pulls a club's premierships from central.premiers (170 rows across 27 clubs, each with a confidence flag), presents each for accept/edit/reject, and writes accepted rows into the tenant-scoped premierships tables as curated rows tagged provenance: central-seed. Central is never written; seeded rows are born as tenant-owned curated content the club can override — preserving the "curated overrides stay tenant-side" rule while ending the blank-honour-board day one.
Basis
direct: all moat tables (honour boards, premierships, life members, awards) are seeded empty at provision — provisionTenant() touches only the tenant row and crosswalk (verified); CLAUDE.md's own mapping table prescribes exactly this: "Premierships honour board | curated | seed from central.premiers (respect confidence; curated overrides stay tenant-side)."
Rationale
Highest value per unit of effort in the set. The product pitch is "your full history instantly," yet the tables that carry the differentiating asset open blank — a 100-year-old club sees zero premierships on day one. The seeding source, the confidence rule, and the override model are already specified in the architecture doc; nobody has built the wizard. It is also the difference between a provision-as-pitch reveal link (idea 4) that wows and one that looks unfinished.
Downsides
Needs a provenance-model decision (how seeded rows are flagged, whether re-seeding merges or skips) — a data-model conversation, not a solo call. Low-confidence central rows need careful UX so the concierge doesn't bulk-accept doubtful premierships into a club's official history.

Unified tenant lifecycle state machine + certification gate

Description
One status enum on the tenants table — draft → staging → live → archived → pending_deletion → deleted — with transitions enforced in one place. It serves three roadmap needs at once: onboarding (tenants are born staged, the subdomain serves a branded holding page, and "go live" is an explicit button gated on derived readiness checks — crosswalk coverage equals central participant count, at least one admin exists, the club's own leaderboard query returns rows, brand is set); deletion ("delete" in the UI becomes archived — hidden, logins blocked, data intact — with a scheduled job running idea 3's sweep only after a 30-day grace); and billing later (the dormant entitlements/billing code needs exactly this state to key "past-due → paused" off).
Basis
direct: the tenants schema has no status column (verified — full schema read); tenants are born public today (slug resolution alone routes them); tenants.ts:43-44 comments that plan "drives feature entitlements; enforcement is dormant until BILLING_ENABLED=true"; the readiness checks automate the manual validation the seed script currently prints as instructions (seed-mandurah-tenant.ts:206-214). external: soft-delete + grace is the dominant SaaS deprovision pattern; AWS SaaS Lens onboarding-pipeline pattern.
Rationale
Archive-by-default means the risky 30-table sweep almost never runs — most "delete" requests during a pilot are "this club didn't convert," and curated content is the moat the project has committed to never discarding. Born-staged tenants close a real reputational risk: a Peel club's members will screenshot a blank honour board exactly once. And because the same column is the missing signal for two dormant subsystems, this is scaffolding three future phases stand on. Retrofitting a status column after "does tenant exist?" checks proliferate is a painful migration — the cost of deferring grows monotonically.
Downsides
Touches tenant routing, login gating, and the platform console at once; the derived-vs-stored health-check design tension (rejections D17/D22) needs resolving inside it. The full six-state machine can ship incrementally (draft/live/archived first).

Platform audit ledger rendered as the tenant activity timeline

Description
One append-only platform_audit_events table (actor, action, target tenant/admin, reason, payload snapshot, IP, timestamp) written by every concierge endpoint from day one — provision, brand change, reset issued, impersonation start/stop, plan change, lifecycle transition, delete. Rendered per tenant as an "Activity" timeline on tenant-detail, so the same rows serve compliance retention and answer the concierge's daily question: "where did we get to with this club?"
Basis
direct: reset-link issuance currently logs which platform admin acted, but "log is transient (console/stdout). No permanent audit table" (impersonation dossier, verified against platform-admin.ts:493-503). external: impersonation audit events warrant the longest retention tier (~36 months) in SaaS audit guidance.
Rationale
This is the one ordering mistake that cannot be repaired retroactively: events never recorded cannot be backfilled. Ideas 1, 2, 3, and 6 all mutate tenant state on a platform admin's say-so — shipping any of them unaudited bakes in permanent blind spots. Making the ledger a working surface (the timeline the concierge reads daily) is what keeps it populated and honest rather than rotting as write-only compliance. Designed generically, it is also the table billing webhooks and entitlement-denial logging will want in Phase 2.
Downsides
Schema shape is a cross-cutting commitment every future feature inherits — worth one deliberate design pass (actor model, payload snapshotting, retention) rather than an incidental table. Small build, but it changes the definition-of-done for every other survivor.
Sequencing note

The set has a natural build order: 7 (audit ledger) underpins everything that mutates tenant state; 6 (lifecycle column) is one migration that both 3 (deletion) and 4 (provision-as-pitch) depend on; 1 (impersonation) and 2 (branding panel) are independent of each other but 1 partially substitutes for 2's UI (the D11/D15 debate — resolve it before building both). 5 (premiers seeding) is standalone and the fastest visible win.
